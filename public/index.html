🤖 Wie funktioniert dieser autonome ERP Support Agent?

Im Gegensatz zu herkömmlichen Chatbots arbeitet dieser Agent mit einer ReAct State Machine (*Reasoning + Acting*). Er generiert nicht einfach nur Text, sondern führt echte, vorbereitete SQL-Statements auf der relationalen SQLite-Datenbank aus und reagiert auf die tatsächlichen Datenbankwerte.

1. ReAct-Zyklus (State-Machine)
  • Thought: Agent begründet logisch den nächsten Diagnoseschritt.
  • Action: Wählt zielgerichtet 1 von 4 SQL-Tools.
  • Observation: Wertet Datenbankergebnisse & Fehlerflags aus.
  • Final Answer: Liefert präzise Analyse oder 2nd-Level Ticket.
2. Die 4 echten SQL-Tools
  • lookup_order_status: Auftrag, Positionen & Sync-Status.
  • check_inventory_and_supplier_feed: Physischer Bestand vs. Reservierung & Zulauf.
  • analyze_erp_sync_error: Diagnose von Deadlocks & EAN-Prüfsummen.
  • escalate_to_2nd_level: Erstellt Ticket mit sicherem SQL-Patch.
3. Sicherheits-Gatekeeper (SQL-Sanitizer)

Jeder KI-generierte SQL-Patch wird vor Ausführung strikt validiert: Nur UPDATE/INSERT auf erlaubte Tabellen, zwingende WHERE-Klausel (Schutz vor Bulk-Wipes), striktes Verbot von DROP, DELETE, TRUNCATE, ; oder SQL-Kommentaren.

4. Dual-Execution Mode (GitHub Zero-Setup)

Der integrierte deterministische Mock-LLM erlaubt jedem Recruiter / Reviewer, alle 4 Szenarien sofort nach git clone und npm run dev ohne OpenAI- oder Gemini-API-Key vollumfänglich und realitätsnah zu testen.

Das Problem im B2B-Großhandel & E-Commerce

Klassische LLM-Chatbots versagen in der Unternehmenspraxis: Sie besitzen keinen Zugriff auf relationale ERP-Daten, kennen keine Live-Lagerbestände und verstehen keine technischen Synchronisationsfehler (z. B. SQL-Deadlocks, Diskrepanzen zwischen Wawi und Shopware-Bestand).

Support-Mitarbeiter im 1st-Level verbringen bis zu 70 % ihrer Zeit mit monotonen Routine-Lookups in der SQL-Datenbank oder müssen Tickets zeitaufwendig an den 2nd-Level-Support (Entwickler/DBAs) weiterleiten.

Die Lösung: Autonomer ERP-Agent jenseits naiver Wrapper

Dieser Agent implementiert eine vollwertige ReAct State-Machine mit 4 realen SQL-Tools, einem deterministischen Mock-Fallback (ermöglicht sofortigen Test auf GitHub ohne API-Key) und einem Sicherheits-Gatekeeper zur Erzeugung sicherer SQL-Patches.

Die ReAct-Schleife (Reasoning + Acting) führt den Agenten iterativ durch die Untersuchung:

1
Thought

Interne Deduktion & Planung des nächsten Schritts

2
Action

Aufruf eines typisierten SQL-Tools mit Parametern

3
Observation

Auswertung der tatsächlichen DB-Rückgabewerte

4
Final Answer

Antwort an Kunden oder 2nd-Level Ticket

Max Turns Guard: Höchstens 5 Zyklen zur Verhinderung von Endlosschleifen oder unkontrollierten API-Kosten.
1. lookup_order_status(orderId: string)

Führt Prepared JOIN über orders, order_items und inventory aus. Ermittelt Kundennamen, Trackinglink, Lieferstatus und etwaige Sync-Stopps (ON_HOLD).

2. check_inventory_and_supplier_feed(sku: string)

Prüft physical_stock gegen reserved_stock. Flaggt kritische Bestandsüberbuchungen (z.B. -4 verfügbar bei SKU-7740) und liefert Lieferanten-Zulaufdaten mit genauer ETA.

3. analyze_erp_sync_error(errorCode?, entityId?)

Sucht in sync_error_logs. Diagnostiziert Fehlerursachen wie ERR_SQL_DEADLOCK_40001 oder ERR_INVALID_EAN_CHECK_SUM und empfiehlt konkrete Root-Cause Behebungen.

4. escalate_to_2nd_level(customerQuery, diagnosis, sqlPatchSuggestion)

Schreibt ein Ticket in support_tickets mit Status IN_REVIEW. Validiert den beigefügten SQL-Patch über den SqlSanitizer.

Sicherheit: Schutz vor bösartigen oder fehlerhaften Patches

Ein autonomer Agent darf niemals unkontrolliert SQL in der Produktionsdatenbank ausführen. Der integrierte SqlSanitizer blockiert automatisch:

  • Verbot gefährlicher DDL-Befehle: DROP, TRUNCATE, DELETE, ALTER, CREATE werden sofort abgewiesen.
  • Whitelist von Zieltabellen: Ausschließlich inventory, orders, sync_error_logs und support_tickets.
  • Zwingende WHERE-Klausel: Ein UPDATE ohne WHERE (was die gesamte Tabelle überschreiben würde) ist verboten.
  • Injection-Schutz: Semikolons (;) und SQL-Kommentare (--, /*) sind unzulässig.
  • Transaktions-Isolation: Das Ausführen des Patches erfolgt in einer atomaren Transaktion (db.transaction()).

Schritt-für-Schritt Reviewer-Walkthrough

  1. 1-Klick-Szenario starten: Klicke oben auf den roten Button "1. Lieferverzögerung ORD-9821".
  2. Thought-Trace beobachten: Sieh rechts im Live-Inspector, wie der Agent 4 Turns absolviert, den Deadlock aufdeckt, das Lager prüft und einen SQL-Patch vorschlägt.
  3. Patch ausführen: Klicke im unteren Bereich unter "🎫 2nd-Level Tickets & Patches" auf den grünen Button "1-Klick SQL-Patch ausführen".
  4. Ergebnis verifizieren: Wechsle auf den Tab "📦 Lagerbestand": Der verfügbare Bestand von SKU-7740 springt von -4 auf 0!
  5. Zurücksetzen: Klicke oben auf "Reset DB", um jederzeit von vorne zu testen.
